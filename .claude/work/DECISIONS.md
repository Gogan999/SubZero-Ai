# Decisions

- D1 (F2, F3): Keep the Python app and run Pi in a Node.js child process the service starts and talks to over stdin/stdout JSONL — Pi is TypeScript-only, a rewrite would risk the approval flow, and stdio needs no new port or shared secret.
- D2 (F2): API-key providers go straight through `@earendil-works/pi-ai`, not the agent runtime — it sends our exact system prompt with no tools and no agent prompt, and it's stateless like our SQLite history.
- D3 (F5): `claude-bridge/...` models run in an in-memory `pi-coding-agent` SDK session with no tools and only the bridge extension — extensions only load in the agent runtime, and no tools keeps students away from shell or file access.
- D4 (F1): Keep `ClaudeClient` as `AI_BACKEND=anthropic`, the default until Pi has run well on the mini PC, and keep `FakeClaude` for tests — gives a one-setting rollback.
- D5 (F4): Model IDs become `provider/model`, with a migration that prefixes existing rows with `anthropic/` — one unambiguous ID across providers; the Fable/Mythos block stays.
- D6 (F1-F8): Approval, the window, the screener, MENTOR ALERT, limits and rejections stay above the backend and don't change; the screener and titles also run through the chosen backend — the safety flow is model-independent by construction.
- D7 (F2, F6): Pin exact npm versions with a lockfile, install with `npm ci --ignore-scripts`, and bundle the official Node.js 22 LTS zip checked against a pinned SHA-256 — matches the existing build's pinning policy.
- D8 (F5): Bridge models can serve students once an admin turns the provider on and the model passes F4c — Logan's choice on Q1 (2026-10-31), made with the subscription-terms risk explained; an API-key model stays configured as a fallback.
- D9 (S1): Slack DMs go through `ApprovalService.submit` like web messages, with no bypass — keeps one approval flow.
- D10 (F2, F3): Python tests use a fake gateway written in Python; the gateway has its own `node --test` suite with pi-ai's `fauxProvider` — the main suite stays fast and needs no Node or keys.
- D11 (F1, F4b): Each model gets a capability record (web search, tools, thinking, images), and the UI and server only offer a feature the chat's model supports — PR #8's web search is Anthropic's server tool, so other models can't use it.
- D12 (F4c): No model (any provider) can be set as the default, hard-problem or screener model until it passes the stored safety check — the safety prompt and MENTOR ALERT have only been verified on Claude.
- D13 (workflow): The delegated workflow is opt-in via `.claude/WORKFLOW.md`; the root `CLAUDE.md` holds only Project facts — the root file loads in every session and would otherwise change all future threads.
- D14 (workflow): The custom agents don't load in the cloud session, so roles run as the general agent with `model` pinned (Haiku research, Sonnet code/review) and the role file as instructions — same cost split; Logan confirmed 2026-10-31.
- D15 (F1): New module `subzero_ai/ai_backend.py` holds the `AIBackend` protocol, `Capabilities`, `capabilities_for(model)`, `resolve_backend(settings)` and `make_client(settings)`; `AI_BACKEND` is config.env-only, not an admin-page setting — switching runtimes is an install-level choice and a bad value from the web page could take every chat down.
- D16 (F1): An unknown `AI_BACKEND` (or `pi` before F3 lands) doesn't crash the service: `make_client` returns an "unavailable" client whose calls fail with a plain message, and `check` reports FAIL — the setup and admin pages stay reachable to fix it.
- D17 (F2): The gateway is plain Node ESM (`.mjs`), no TypeScript build step; logic in `pi_gateway/lib/gateway.mjs` (`createGateway({models, getApiKey, write})`) so tests can inject a pi-ai `createModels()` collection with the faux provider; `pi_gateway/gateway.mjs` only wires stdin/stdout and `builtinModels()`.
- D18 (F2, F3): The gateway's wire format speaks Anthropic shapes both ways: request `messages` are our Anthropic content blocks (text, base64 image, tool_use, tool_result), usage records use `input_tokens`/`output_tokens`/`cache_read_input_tokens`/`cache_creation_input_tokens` plus `cost_usd`, stop reasons map to `end_turn`/`max_tokens`/`tool_use`, and `tool_turn` returns an Anthropic-style message — the Python side already stores and reads those shapes, so `PiClient` stays thin and all format conversion lives in one place.
- D19 (F2): Provider keys reach the gateway only as `SUBZERO_KEY_<PROVIDER>` env vars (provider id upper-cased, `-` → `_`) and are passed to pi-ai as an explicit per-call `apiKey`; a missing key is an error, never a fallback to ambient `ANTHROPIC_API_KEY`/OAuth/credential stores — no credential the admin didn't configure gets used.
- D20 (F2): For Anthropic Messages models the gateway rewrites pi-ai's request body in `onPayload` to match `ClaudeClient.request_body`: no `thinking` key, no injected `role:"system"` effort-marker messages, `output_config.effort` only when an effort was asked for, and `system_extra` as a second, uncached system block — pi-ai 1.4.0 turns on adaptive thinking for every 5.x Claude model (`supportsMidConvoEffort`), which would change cost, latency and replies versus today; pi-ai is pinned and tests on the real 5.x model records catch drift.
- D21 (F2): From pi-ai's Anthropic body we also drop the mid-conversation-output-config and thinking-binding-controls betas (their features are stripped by D20) but keep pi-ai's tool extras (deferred placeholder tool, inline-tools beta, eager streaming) as built — they're pi-ai's own tested tool path; a live check comes with F5/F7.
- D22 (F3): `PiClient` runs the gateway with `subprocess.Popen` plus reader threads (handing records to the event loop with `call_soon_threadsafe`), not asyncio subprocesses — uvicorn on Windows may run a selector event loop that can't spawn asyncio subprocesses, and `ClaudeClient` already uses the thread pattern. The gateway starts lazily on the first request, so building services never spawns Node.
- D23 (F3): The child gets a minimal environment (system vars Node needs, proxy/CA vars, and `SUBZERO_KEY_*`), never the service's whole environment — keeps D19's "only configured keys" promise. Until F4, a bare `claude-...` id is sent as `anthropic/claude-...`.
- D24 (F3, F4b): Under `AI_BACKEND=pi`, web search isn't available (the gateway has no Anthropic server tools): `capabilities_for(model, backend)` reports `web_search=False` for the pi backend, and `PiClient.stream(web_searches>0)` answers without search and logs a warning; F4b hides the buttons.
- D25 (F4): Provider keys live in config.env like the Anthropic key (which is only entered on the setup page today, not the Settings page as the plan assumed): fixed fields `openai_api_key`, `gemini_api_key`, `openrouter_api_key` (env `OPENAI_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`), all key fields `repr=False`. A new admin-only "AI providers" box on the Settings page saves them to config.env, never shows them back (only "saved"/"not set"), and audits the provider name only — backups already exclude config.env.
- D26 (F4, Q2): Supported providers are anthropic, openai, google, openrouter; a saved `ai_providers` setting (admin page) turns them on, default `anthropic` only. Model settings must be `provider/id` with an enabled provider; under `AI_BACKEND=anthropic` only `anthropic/` models are allowed. OpenRouter covers most other models with one key.
- D27 (F4): Bare `claude-...` ids are normalized to `anthropic/claude-...` everywhere: migration 11 rewrites `conversations.model`, `messages.model`, `code_sessions.model` and saved model settings; config.env values are normalized at load; `ClaudeClient` strips `anthropic/` before calling the API and refuses other providers with a plain error.
- D28 (F4): After an admin saves a key, the running client picks it up without a restart: `PiClient.set_keys()` swaps the child env and restarts the gateway once it's idle; the screener, health, generation and code runner keep their one shared client object.
- D29 (F4b, Q7): Capabilities gain `code` (Code sessions: Anthropic Claude models only, per Q7's default). For non-Claude models `images`/`thinking` come from the gateway's model info (`input` has image, `reasoning`), cached on Services next to the names; unknown → off. The composer hides what the chat's model lacks (new-chat pages use the default model), the server refuses a forced option or image with a plain 400, and at reply time (e.g. after a mentor switched models) unsupported options are dropped and history images are replaced by a short text note, so a pending message never fails because of the switch.
- D30 (F4b): `Capabilities.code` is a normal field that takes part in equality; the old 4-field test expectations were updated — equality should mean what it says.
- D31 (F4c): The safety check mixes exact checks with a judge model: MENTOR ALERT (reply must start with the marker; a normal question must not), explainer fence (render.explainers) and screener SAFE/REVIEW parsing are checked in code; "refuses the unsafe request" and "ignores a prompt injection" are graded by a judge model (`model_check_judge`, default `anthropic/claude-sonnet-5-5`) answering one line `PASS` / `FAIL: reason`. Any error or malformed grade counts as a fail (fail closed). Keyword matching for refusals would be too easy to fool.
- D32 (F4c): Results go in a new `model_checks` table (migration 12) with the model, chat/screener pass flags, per-case details, judge, check version, actor and time. A new value for the default or hard-problem model needs a passing chat check, and a new screener value needs a passing screener check, from the current check version. Models already saved when 0.5 installs keep working without one (they're grandfathered), but `check` WARNs about them. The admin's run happens in the background (Cloudflare cuts long requests), and the page shows the latest results.
- D33 (F4c): A check refuses to start unless the judge's provider is on and has a key (plain message naming the judge). LLM judging has some leftover injection risk, so the candidate's reply goes to the judge in delimited, escaped tags with a strict one-line grade, and the judge's default is a strong Claude model. We accept that leftover risk.
- D34 (F5): The bridge runs Claude Code with `tools: []` but also `permissionMode: "bypassPermissions"`, inherits the parent env, and replays history by writing Claude Code session JSONL files. We can't check here that `tools: []` really turns off every built-in tool, so the gateway adds its own guards: (1) an empty, throwaway working folder under DATA_DIR per reply; (2) `CLAUDE_CONFIG_DIR`/`PI_CODING_AGENT_DIR` under DATA_DIR, with that reply's session files deleted afterwards; (3) the child env is the minimal env without any `ANTHROPIC_*` key (otherwise Claude Code switches to API billing); (4) if any tool-call event appears in a bridge reply, the reply is aborted and errored and the event is logged; (5) the admin toggle starts off. The mini-PC spike (latency, MENTOR ALERT format, no tool use) is still required before students use it.
- D35 (F5): Bridge replies hold a cross-process lock file (`bridge/reply.lock`, exclusive create, holder pid inside; taken over when that pid is dead or the lock is older than the request timeout), because an old and a new gateway can overlap after `set_keys`/`set_bridge`. Under the lock, the gateway sweeps at startup and after every reply: it empties `bridge/work/`, deletes everything in `claude-config` except a keep list (`.credentials.json`, `.claude.json`, our `settings.json`), and strips any `projects`/history keys from `.claude.json`. A keep list (rather than a list of folders to delete) means new Claude Code folders get cleaned too, and a crash mid-reply leaves nothing behind after the next start. The gateway also writes a restrictive `claude-config/settings.json` (deny every tool, `disableAllHooks`, no plugins/MCP) and rewrites it before each reply. If abort doesn't finish within 10 s, the session is dropped so the queue keeps moving. K2 accepted: on Linux a same-user child could still read the parent's original environment through /proc; the target is Windows, so this doesn't matter there.
- D36 (F6): The release stays one zip. Node.js v22.23.4 (official win-x64 zip, SHA-256 cbc74b5e…5f20 from nodejs.org SHASUMS256) unpacks to `<install>\node\`, and the gateway with its win32-x64 node_modules (`npm ci --ignore-scripts --omit=dev --os=win32 --cpu=x64`) goes to `<install>\app\pi_gateway\`, so the Claude Code binary for the bridge (~320 MiB) is included. That makes the zip much bigger, but users keep downloading one file, and the bridge still starts off. `PI_NODE` empty (the new default) means `<install>\node\node.exe` if it's there, otherwise `node` on PATH.
- D37 (F6): At build time, prune `*.d.ts`/`*.d.mts`/`*.d.cts`, `*.map` and `node_modules/.bin` from the gateway's node_modules. Keep every `.ts` source (the bridge is loaded through jiti), every README/docs file (pi-coding-agent reads them) and every LICENSE/NOTICE. update.ps1 unpacks to a short temp path (`SZ-<stamp>\\u`), and the build's path guard uses the worst-case update prefix (~100 chars) with a 259 limit. That roughly halves the file count, and updates keep working for long Windows usernames.
- D38 (F7): The regression suite runs the existing flow tests (test_flow, test_approval_window, test_slack_interactions) against three backends through one mixin/parameter: FakeClaude directly; ClaudeClient with a fake requests.Session that turns FakeClaude's canned behaviour (magic words included) into Anthropic SSE/JSON; and PiClient with tests/fake_pi_gateway.py in a 'fakeclaude' mode that does the same over the gateway protocol. Every backend sees the same scripted model behaviour, so any difference in the results comes from the client and transport code, not from the replies.

## S1 Slack DMs (2026-10-31, after PR #11 merged)
- D39. New `subzero_ai/slack_dm.py` (`SlackDMs`); `SlackInteractions.dispatch` routes `events_api` message.im envelopes to it, acks at once, works in a spawned task.
- D40. Ignore subtypes, bot messages, the bot's own user and empty text; dedupe Slack retries on (channel, ts) before submitting.
- D41. One chat per Slack thread (Q6). Top-level DM starts a chat; a thread reply continues the linked chat; an unlinked thread gets a "start a new message" note.

- D44. Thread notes: errors show the Outcome message; pending gets "A mentor will check this…" and, for a new chat, a website link noting the team can see approved chats.

- D47. Small Markdown → Slack mrkdwn converter, 3500-char chunks; explainers become a website link; sources listed.
- D48. Outcome of review for DM messages posted in the thread through a hook (rejection reason student-only; edited note).
- D49. `SLACK_DMS` setting (default on), admin-overridable.
- D50. Manifest: writable Messages tab, `im:history`, `message.im` event; README permissions + student-facing section; Logan reinstalls the app.

## Code-only pivot, v0.11.0 (2026-11-14)
- D52 (all): Scope and Logan's decisions are in PLAN.md; the plan doc is the reference. One PR, features committed one by one.
- D53 (F1): Shared page helpers move to `web_common.py`; `web.py` re-exports them so no test changes in F1 — proves the move changed nothing.
- D54 (F3): No table is dropped and no data deleted in this release; removed features only lose their code and pages — rollback to v0.10.0 stays a file copy.
- D55 (F3b): The mentor chat page reuses `/c/{id}` (mentors/admins only, read-only, review buttons); students are redirected to `/code` — Slack cards already link there.
- D56 (F3b): Review-action routes keep their authorisation inside `ApprovalService` exactly as today — approval flow is off-limits.
- D57 (G3): "Everything ships enabled" means these defaults: `code_engine=agent`, `code_sandbox=hyperv`, `code_student_access=True`, plan-first available (off per session unless ticked; default tick from a setting, on for students), sub-agents on, web tools on for mentors and students (gateway-enforced switch per role). A one-time upgrade step sets engine/sandbox/student access on existing installs too and audits it — Logan's instruction of 2026-11-14 overrides the plan's "off until tested".
- D58 (G3): The fallback is one Settings field "Code engine": "New engine (sandbox only)" or "Classic engine". Classic keeps today's behaviour, including mentor sessions without a sandbox.
- D59 (G3): Test mode (`FAKE_CLAUDE=1` / fake sandbox) keeps working offline: with the fake sandbox the agent engine starts a local fake runner; tests pin the settings they rely on rather than depending on defaults.
- D60 (G1): The gateway is a hand-written asyncio HTTP/1.1 server (same style as `egress_proxy.py`, no new dependency) on `sandbox_host_address` and new `sandbox_gateway_port` (default 3129). It starts only with the sandbox on and the agent engine selected.
- D61 (G1): Auth = the sandbox's existing egress token, sent by the SDK as `Authorization: Bearer` (`ANTHROPIC_AUTH_TOKEN`), checked with the same `TokenStore` and peer-address tie as the proxy. Token → sandbox → Code session. No token, wrong address or unknown session: 401, nothing forwarded.
- D62 (G1): Forwards only `POST /v1/messages` (stream or not) and `POST /v1/messages/count_tokens`; answers `GET /v1/models` and `HEAD|GET /api/hello` locally; everything else 404. Upstream is `anthropic_base_url` or api.anthropic.com. Incoming credential headers are dropped; the real one is added on the host.
- D63 (G1): Per request the gateway enforces: model in the session's allowed set (Settings models), else 400; appends the team's safety rules as a final `system` text block (never touching the first block); strips server web tools (`web_search*`, `web_fetch*`) when the session isn't allowed web tools; refuses when the session's spend is at its cap (HTTP 402-style error JSON the SDK surfaces).
- D64 (G1): Usage is counted from the upstream reply (JSON `usage`, or SSE `message_start` + cumulative `message_delta`) and priced with `pricing.cost_usd`; totals are kept per Code session through a small callback interface so the gateway has no DB code of its own. One cap in API-equivalent dollars for both sign-in kinds (subscription shows it as "about $X at API prices") — simpler than a second token cap.
- D65 (G1): Credentials: `api_key` → `x-api-key: <anthropic_api_key>`; `subscription` → `Authorization: Bearer <token>` + `anthropic-beta` gains `oauth-2025-04-20`. The subscription token is a new secret `code_subscription_token` in config.env (from `claude setup-token`); if empty, the gateway reads `claudeAiOauth.accessToken` from the bridge credentials file when present and unexpired. Both paths are unverified against Anthropic until the mini PC test; errors are surfaced plainly.
- D66 (G1): Secrets never appear in logs, errors or step output; upstream error bodies are passed through but request headers are never echoed.
- D67 (G2): Runner protocol (JSON lines). Host → runner: `{type:"start", task, model, cwd, resume?, plan_first, allowed_web, sub_agents, max_turns, append_system}`, `{type:"message", text}`, `{type:"plan_decision", approve, note}`, `{type:"stop"}`. Runner → host: `{type:"ready", runner_version, sdk_version}`, `{type:"session", session_id}`, `{type:"text", text}`, `{type:"tool_start", id, name, input, parent_id?}`, `{type:"tool_end", id, output, is_error}`, `{type:"plan", id, plan}`, `{type:"todo", items}`, `{type:"compact"}`, `{type:"turn_done", usage, cost_usd, num_turns, is_error, error?}`, `{type:"error", message, detail?}` (detail is for logs only, never shown to users). One runner process per run; it stays alive for queued follow-ups until stdin closes or `stop`.
- D68 (G2): Runner uses `query()` with streaming input, `systemPrompt` preset `claude_code` + append, `settingSources: ["project"]` (so the repo's CLAUDE.md is read), `permissionMode: "bypassPermissions"` (non-root `sandbox` user in a throwaway VM) or `"plan"` when plan-first; in plan mode `canUseTool` holds `ExitPlanMode` until the host's `plan_decision`, then switches to bypass via `setPermissionMode`. The exact plan-approval mechanics are unverified in SDK 0.3.316 and get checked on the mini PC.
- D69 (G2): The runner gets its endpoint and token from env set by the host for that run (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`), with telemetry, auto-update and non-essential traffic off. It never sees a real key.
- D70 (G2): `tests/fake_agent_runner.py` speaks the same protocol with scripted behaviour (magic words in the task) so the driver is tested offline; `sandbox_runner/test/` has node tests for the runner's own mapping with a stubbed SDK.
- D71 (G3): Migration v17 only adds columns to `code_sessions` (`engine TEXT NOT NULL DEFAULT 'classic'`, `agent_session_id TEXT`, `plan_first INTEGER NOT NULL DEFAULT 0`, `cost_usd REAL NOT NULL DEFAULT 0`, `cap_usd REAL`) — v0.10.0 ignores them, so rollback still works. No new status values (the CHECK constraint stays).
- D72 (G3): Agent events become `code_steps` with the existing kinds: text → `text`; tool calls → `tool` with the SDK tool name; plans → a `tool` step named `plan` with status `pending` that the existing step-decision route approves or declines; notes → `note`.
- D73 (G3): Two agent sessions run at once (`code_max_running`, default 2); others stay `preparing` with a note "Waiting for a free sandbox" and start in order. `sandbox_memory_mb` default becomes 6144.
- D74 (G3): The patch comes from the VM: base commit made at prepare, `git diff --binary` against it at the end of each run, stored where the classic engine stores its patch so release/download are unchanged.
- D75 (G3): Student rules are enforced before anything reaches the runner, in the same `CodeRunner` entry points as today (request, decide_request, request_follow_up, decide_follow_up); the agent engine is refused without a sandbox for everyone.
- D76 (G3): Caps: `code_cap_student_usd` 5, `code_cap_mentor_usd` 15, editable. Reaching the cap stops the run with a plain note.
